# Windows 端行为验收（命令行路径）

两个脚本，验的是**只能在 Windows 上暴露**的那些行为 —— 在 macOS 上全绿，
换到 Windows 才出问题，且多半是静默失败。

## 跑法

```bash
cd apps/pic2webp/tests/windows

# 1) 先生成样张（需要 Pillow：pip install pillow）
python make_fixtures.py

# 2) 再跑验收（第一个参数是 pic2webp.exe 的路径）
python check_cli.py H:/p2w-target/release/pic2webp.exe
```

退出码：0 = 全绿，1 = 有 FAIL。样张落在 `in/`，产物落在 `out/`，两者都在 `.gitignore` 里。

## 为什么要有它

2026-11-26 在 Windows 本机首跑时，这套脚本一次揪出**两个真缺陷**：

| 缺陷 | 症状 | 修法 |
|---|---|---|
| 后端格式白名单漏 `.tif` | 面板里能选、列表里也进得去，点转换**一个产物都不出**；双击 `.tif` 更是只开一个空窗口 | 三处白名单收敛成一张表（`f398c83`） |
| 命令行不应用 EXIF 方向 | 同一张 iPhone 竖拍照片，**界面里是正的、脚本跑出来是躺的**，两边都"成功" | 两条路收敛到同一个 `decode_oriented`（`e27c940`） |

两个都是「不报错、不崩溃、只是结果不对」的形态 —— 没有真机验收就永远发现不了。

## 覆盖的行为

- 基本转换 + 颜色保真（左红右蓝顶绿，逐像素核对）
- EXIF 方向 6 / 8 / 5 / 7 转正
- `.tif` 能被转换出产物、尺寸不变
- 中文文件名 + 带空格的文件名
- `--recursive` 扫子目录
- 16-bit 灰度渐变未塌成 8-bit（实测 219 级，阈值 >200）
- 批量转换产物数与输入数对得上
- 单张大图耗时（4000×3000 → WebP q80 约 0.8 s）

## 两个已知行为（不是缺陷，别去"修"）

- **CLI 收到 `.heic` / `.heif` 照样出文件**：CLI 按**内容嗅探**解码，不按后缀过滤；
  样张里的 `fake.heic` 内容其实是 JPEG。产品本身**不支持 HEIC**（专利许可限制），
  图形界面侧才按白名单跳过并提示「不支持 HEIC」。
- **CLI 同名输出会覆盖**：`fake.heic` 与 `fake.heif` 的 stem 相同，输出文件名撞车，
  后写的覆盖先写的。CLI 没有图形界面那套撞名保护 —— CLI 是内部接口，
  官网与 README 都没对外承诺这个行为。

## 与判据的关系

这两个是**真机行为验收**，跑一次要几秒、要看产物；
仓库里的 `tests/formats.test.mjs` 才是**每次提交都跑的判据**（静态、正反对照）。
两者互补：判据盯住「代码形状对不对」，这套脚本盯住「跑起来对不对」。
